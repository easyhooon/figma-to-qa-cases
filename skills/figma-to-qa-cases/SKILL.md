# Figma 기획서 → QA 테스트 케이스 엑셀

기획서에 **정의되지 않은 동작(미정의 항목)** 을 먼저 찾아 질문으로 만들고, 답을 기다리지 않고 권장값을 가정으로 둔 TC 를 만든다. 기획자 답이 오면 가정이 걸린 TC 만 고친다.

- 미정의 항목: 기획서에 적혀 있지 않아 TC 의 기대 결과를 정할 수 없는 정보. 예: 기획서에 "+100ml 탭 시 100ml 씩 증가"만 있고, 목표에 도달한 뒤 다시 누르면 어떻게 되는지는 없다.
- 이 스킬의 목적은 사람의 작업을 줄이는 것이다. 초안과 질문을 만들 뿐, 사람의 검토와 판단을 대체하지 않는다.
- 질문은 기획자가 고르기만 하면 되게 만들고, TC 작성은 답을 기다리지 않는다. 사람 사이 합의가 병목이 되지 않게 하기 위해서다.

이 문서 기준 경로: `<skill>` = 이 SKILL.md 가 있는 폴더.

## 준비 (처음 한 번)

1. 스크립트는 Node 18+ 과 `exceljs` 가 필요하다. 플러그인 루트(`<skill>/../..`)에서 `node -e "import('exceljs')"` 가 실패하면 `npm install --prefix <플러그인 루트>` 를 실행한다.
2. PDF 모드는 `pdftotext`, `pdftoppm`(poppler)이 필요하다. 없으면 사용자에게 `brew install poppler`(macOS) 설치를 안내한다.
3. 프로젝트 루트에 `.qa-cases.json` 이 있는지 본다. 없으면 [`references/config.md`](references/config.md) 의 기본값을 보여 주고 사용자 확인 후 만든다.
4. `.gitignore` 에 `<outputDir>/*/snapshot/` 이 있는지 본다. `.gitignore` 가 없으면 만든다. 있는데 줄이 없으면 넣을 줄을 사용자에게 보여 주고 확인받은 뒤 추가한다. 이유: 스냅샷은 공개하면 안 되는 기획 문서 원본이고, 기존 설정 파일은 확인 없이 고치지 않는다.

- 넘어가는 조건: 설정의 `outputDir`, `decisions`, `idScheme` 을 안다.

## 입력

- 기능 이름(영문 케밥케이스. 예: `water-log`). 파일 이름에 쓴다.
- 모드: `mcp`(Figma 링크만) 또는 `pdf`(Figma 메타데이터 + 섹션 PDF). **고르는 기준, PDF 를 쓰는 이유, 모드별 절차는 [`references/input-modes.md`](references/input-modes.md)** 를 읽고 따른다. 모르면 사용자에게 Figma dev seat 이 있는지 묻는다.

아래에서 `<out>` = 설정의 `outputDir`, `<snap>` = `<out>/<기능 이름>/snapshot`, `<draft>` = `<out>/<기능 이름>.draft.json`. `draft.json` 형식은 `<skill>/scripts/cases-to-xlsx.mjs` 상단 주석.

## 절차

각 단계는 "넘어가는 조건"을 만족해야 다음 단계로 간다.

### 0. 결정 사전 읽기

설정의 `decisions` 파일(이미 기획자와 합의한 기본값 목록)을 읽는다. 없으면 [`references/decisions-template.md`](references/decisions-template.md) 의 "복사할 부분"만 복사해 만든다(묻지 않는다).

- 넘어가는 조건: 사전 항목 ID(`D-xx`) 목록을 파악했다(0개여도 된다).

### 1. 스냅샷 만들기와 범위 확정

`<snap>/frames.json` 이 이미 있으면 Figma 를 다시 읽지 않는다. 사용자가 "기획서가 바뀌었다"고 할 때만 다시 만든다. 이유: seat 없는 계정은 MCP 호출 한도가 작다.

모드별 절차는 [`references/input-modes.md`](references/input-modes.md) 2, 3장.

- 범위의 화면 수는 `frames.json` 에서 `screen: true` 인 묶음만 센다(섹션 제목 배너 등은 빼고). 15개를 넘으면 목록을 보여 주고 이번 범위를 사용자에게 고르게 한다. 이유: 질문이 수십 개가 되면 기획자가 답하지 않는다.
- 넘어가는 조건: 스냅샷이 저장됐고, 이번 범위 화면 목록(화면 ID, 이름)을 사용자에게 한 번 보여 줬다.

### 2. 기획서 사실 정리

화면마다 기획서에 **적혀 있는 것만** `<draft>` 의 `facts` 에 쓴다: 진입 경로, 사용자 동작, 화면 이동(`arrows.json` 포함), 노출 문구, 그려진 상태.

- 사실마다 근거 위치 `where` 를 붙인다. 주석 번호가 있으면 `SCR-03 #8` 처럼 화면 ID + 주석 번호. 이유: 기획자가 바로 찾을 수 있는 가장 짧은 위치다.
- **앱 소스 코드에서 기대 결과를 가져오지 않는다.** 이유: 구현에서 뽑은 기대 결과는 버그를 "정상"으로 확정한다.
- 따옴표로 옮길 문구(버튼, 플레이스홀더, 안내 문구)는 **화면 이미지로 확인한다.** 시안 영역 텍스트도 `1 000 ml`, `[HL-02-8 ]` 처럼 깨져 나온다. 짝이 안 맞는 따옴표는 바로잡아 옮긴다.
  - 건너뛰고 싶어지는 이유: "frames.json 텍스트로 충분해 보인다" → 숫자 쉼표와 화면 ID 가 깨진 채 TC 에 들어간다. 첫 실행에서 실제로 일어났다.
- 넘어가는 조건: 범위 화면마다 사실이 있고 각 사실에 `where` 가 있다.

### 3. 미정의 항목 찾기

[`references/undefined-checklist.md`](references/undefined-checklist.md) 의 유형별로 정의되지 않은 동작을 찾아 `<draft>` 의 `undefinedItems` 에 쓴다. 항목 하나마다:

1. 결정 사전에 해당 항목이 있으면 그 값을 쓰고 `status: "dictionary"`, `basis: "D-xx"` 로 적는다. 질문하지 않는다.
2. 없으면 질문을 만든다(체크리스트 2장). `question`(TC 작성자용 한 줄)과 `ask`(기획자에게 보내는 질문 문장)를 따로 쓴다. **권장값과 근거를 반드시 붙인다.** 이유: 빈 질문은 기획자가 정책을 처음부터 만들어야 해서 답이 늦다.
3. 차단형/비차단형으로 나눈다(체크리스트 1장).

- 차단형 10개는 **상한**이지 목표가 아니다. 답에 따라 TC 의 절차나 기대 결과, 개수가 실제로 바뀌는 것만 차단형이다. 10개를 넘으면 영향 TC 가 적은 것부터 비차단형으로 옮긴다.
- ID 는 `U-01` 부터 차단형 먼저, 그 안에서 체크리스트 유형 순서로 매긴다.
- 체크리스트 유형 중 항목이 0개인 유형은 7단계 보고에 "해당 없음(이유)"으로 적는다.
- 넘어가는 조건: 모든 항목에 ID, `where`, `question`, `ask`, `options`, `recommended`, `basis` 가 있다.

### 4. 질문 전달 (기다리지 않는다)

사용자에게 미정의 항목 목록을 보여 주고, 기획자에게는 `<out>/<기능 이름>.questions.md`(6단계에서 생성, 엑셀의 기획자 전달 문구 열과 같은 내용)의 질문을 그대로 보내면 된다고 알린다(Figma 해당 프레임 댓글 권장). 기한은 사용자에게 묻고, 답이 없으면 영업일 2일 뒤로 둔다.

건너뛰고 싶어지는 이유와 왜 안 되는지:

- "사소한 항목이니 권장값으로 TC 만 만들자" → 질문을 안 보내면 기획자는 가정이 있었는지도 모른다. 비차단형도 목록은 전달한다.
- "답을 받고 나서 TC 를 만들자" → 사람 합의가 병목이 된다. 답이 와도 바뀌는 건 가정이 걸린 TC 뿐이다.

- 넘어가는 조건: 목록을 사용자에게 보여 줬다.

### 5. 테스트 케이스 작성

`<draft>` 의 `cases` 에 쓴다.

- TC ID 는 설정 `idScheme` 을 따른다.
  - `spec`: 기획서가 화면 ID 와 주석 번호(①②…)를 쓰는 경우. TC ID = `<화면 ID>-<주석 번호 두 자리>-<순번 두 자리>`(예: `SCR-03-08-01` = SCR-03 화면 주석 ⑧의 첫 케이스). 케이스에 `screenId`, `annotation` 을 함께 넣는다.
    - 이유: TC 와 기획서 위치가 1:1 로 이어져, 주석 하나가 바뀌면 영향 받는 TC 를 ID 만 보고 찾는다.
    - 동작을 설명하는 주석이 다른 화면에 있으면(예: 주석 없는 상태 화면 SCR-04 의 버튼 동작을 SCR-03 주석 ⑧이 설명) 그 주석의 화면 ID 와 번호를 쓴다.
    - 주석 번호가 없는 요소(화면 제목, 안내 문구 등)는 그 요소가 있는 화면 ID 에 `00` 을 쓴다.
  - `feature`(기본): `<기능 약어>-<두 자리 번호>`. 기획서에 화면 ID 나 주석 번호가 없을 때.
- 기대 결과 하나에 확인 하나. 이유: 두 확인을 섞으면 한쪽만 틀려도 원인을 못 가른다.
- 사전조건에는 결과를 바꾸는 사용자 상태를 빠짐없이 쓴다(예: 키 입력 여부, 기록 유무, 목표 설정 여부). 이유: 빠지면 QA 가 다른 상태로 실행해 앱 문제 없이 실패한다. 체중 기록 실행에서 키 정보가 빠진 TC 가 나왔다.
- 케이스마다 근거 사실 ID 를 `facts` 에, 기대는 미정의 항목 ID 를 `assumptions` 에 넣는다. 모든 사실과 미정의 항목이 TC 하나 이상과 이어져야 하고, 스크립트가 검사한다. 잇지 않을 이유가 있으면 그 항목에 `noCase` 로 적는다.
- 자동화 여부처럼 다음 단계 도구가 정하는 열은 비워 둔다. 이유: 여기서 추측하면 틀린다.
- 넘어가는 조건: 6단계 스크립트가 연결 검사를 통과한다.

### 6. 엑셀 만들기

```
node <skill>/scripts/cases-to-xlsx.mjs <draft> --config .qa-cases.json
```

- 오류가 나면 메시지대로 `<draft>` 를 고친다. 엑셀을 직접 고치지 않는다(다시 만들면 덮어써진다. 이전 엑셀은 `.prev.xlsx` 로 남는다).
- 넘어가는 조건: 오류 없이 끝나고 TC 수, 미정의 항목 수가 출력됐다.

### 7. 보고

엑셀 경로, 기획자에게 보낼 질문 파일(`<기능 이름>.questions.md`) 경로, TC 수, 차단형/비차단형 수, 결정 사전으로 처리한 수, 가정이 붙은 TC 수, 해당 없음 유형과 이유, MCP 호출 횟수, PDF 모드면 "댓글 미반영"을 알린다.

### 8. 기획자 답 반영 (답이 온 뒤 다시 호출될 때)

1. 답이 온 항목의 `status` 를 `confirmed`(권장값 그대로) 또는 `changed`(`answer` 에 실제 답, "기타"로 직접 쓴 답도 그대로)로 바꾼다. 기한이 지나도록 답이 없는 항목은 스크립트가 "기한 경과, 권장값 확정"으로 표시하므로 그대로 둔다. 답이 온 항목의 기획자 전달 문구는 스크립트가 "(답 반영됨, 다시 보내지 않음)"으로 바꾼다.
2. `changed` 항목마다 TC 를 이렇게 고친다.
   - 그 항목을 `assumptions` 에 가진 TC 중 답과 어긋나는 것은 고치거나 지운다. 어긋나지 않는 것은 그대로 둔다.
   - 답이 새로 정한 동작은 **그 동작이 나오는 모든 화면**에 TC 를 추가한다(예: 입력 자릿수 제한이 정해지면 같은 입력란이 있는 바텀시트마다). 이유: 한 화면에만 추가하면 같은 규칙의 다른 화면이 빠진다.
   - 추가한 TC 의 순번은 같은 주석의 마지막 순번 다음을 쓰고, 지운 ID 는 다시 쓰지 않는다. 그 밖의 TC 는 건드리지 않는다.
   - 비차단형이었는데 답 때문에 TC 가 생기거나 없어지면 `blocking: true` 로 바꾸고 보고에 적는다. 다음 기능의 분류에 참고한다.
3. 다른 기능에도 쓸 만한 결정은 결정 사전에 바로 넣지 말고 보고에 "결정 사전 후보"로 적는다. 사용자가 확인하면 근거와 함께 추가한다.
4. 6단계로 엑셀을 다시 만든다.

## 금지

- 기획서에 없는 기대 결과를 미정의 항목 없이 TC 에 넣지 않는다. 이유: 기획자도 QA 도 모르는 기준이 생긴다.
- 기획자에게 직접 메시지나 댓글을 보내지 않는다. 전달은 사용자가 한다.
- 요청받지 않은 기존 엑셀, 테스트 코드, 설정을 고치지 않는다(준비 4번의 `.gitignore` 는 확인받은 뒤에만).
- 스냅샷(기획서 원본)을 git 에 올리지 않는다.
