# Figma 기획서 → QA 테스트 케이스 엑셀

기획서의 공백을 **먼저** 질문으로 만들고, 답을 기다리지 않고 권장값을 가정으로 둔 TC 를 만든다. 기획자 답이 오면 가정이 걸린 TC 만 고친다.

이 스킬의 핵심은 사람 합의를 병목으로 만들지 않는 것이다. 질문은 기획자가 "고르기만" 하면 되게 만들고, TC 작성은 답을 기다리지 않는다.

이 문서 기준 경로: `<skill>` = 이 SKILL.md 가 있는 폴더.

## 준비 (처음 한 번)

1. `<skill>/scripts` 의 스크립트는 Node 18+ 과 `exceljs` 가 필요하다. `node -e "import('exceljs')"` 가 `<skill>/../..`(플러그인 루트)에서 실패하면 `npm install --prefix <플러그인 루트>` 를 실행한다.
2. PDF 모드는 `pdftotext`·`pdftoppm`(poppler)이 필요하다. 없으면 사용자에게 `brew install poppler`(macOS) 설치를 안내한다.
3. 작업 중인 프로젝트 루트에 `.qa-cases.json` 이 있는지 본다. 없으면 [`references/config.md`](references/config.md) 의 기본값을 보여 주고, 사용자 확인 후 만든다.
   - 넘어가는 조건: 설정의 `outputDir`, `decisions` 경로를 안다.

## 입력

- 기능 이름(영문 케밥케이스. 예: `water-log`). 파일 이름에 쓴다.
- 모드: `mcp`(Figma 링크만) 또는 `pdf`(Figma 링크 + 섹션 PDF). **고르는 기준과 PDF 를 쓰는 이유는 [`references/input-modes.md`](references/input-modes.md)** 를 읽고 따른다. 모르면 사용자에게 Figma dev seat 이 있는지 묻는다.

아래에서 `<out>` = 설정의 `outputDir`, `<snap>` = `<out>/<기능 이름>/snapshot`.

## 절차

각 단계는 "넘어가는 조건"을 만족해야 다음 단계로 간다.

### 0. 결정 사전 읽기

설정의 `decisions` 파일(이미 합의한 기본값 목록)을 읽는다. 없으면 [`references/decisions-template.md`](references/decisions-template.md) 로 만들지 사용자에게 묻는다.

- 넘어가는 조건: 사전 항목 ID(`D-xx`) 목록을 파악했다(0개여도 된다).

### 1. 스냅샷 만들기와 범위 확정

`<snap>` 이 이미 있으면 Figma 를 다시 읽지 않는다(사용자가 "기획서가 바뀌었다"고 하면 다시 만든다). 이유: seat 없는 계정은 MCP 호출 한도가 작다.

모드별 절차는 [`references/input-modes.md`](references/input-modes.md) 2·3장.

- 프레임이 15개를 넘으면 목록을 보여 주고 이번 범위를 사용자에게 고르게 한다. 이유: 질문이 수십 개가 되면 기획자가 답하지 않는다.
- 넘어가는 조건: 스냅샷이 저장됐고, 이번 범위 화면 목록(ID, 이름)을 사용자에게 한 번 보여 줬다.

### 2. 기획서 사실 정리

화면마다 기획서에 **적혀 있는 것만** 정리한다: 진입 경로, 사용자 동작, 화면 전환, 노출 문구, 그려진 상태.

- 모든 사실에 근거 위치를 붙인다. 주석 번호가 있으면 `HL-02-25 #8` 처럼 화면 ID + 주석 번호. 이유: 기획자가 바로 찾을 수 있는 가장 짧은 위치다.
- **앱 소스 코드에서 기대 결과를 가져오지 않는다.** 이유: 구현에서 뽑은 기대 결과는 버그를 "정상"으로 확정한다.
- 넘어가는 조건: 화면별 사실 목록이 있고 각 항목에 근거 위치가 있다.

### 3. 공백 찾기

[`references/gap-checklist.md`](references/gap-checklist.md) 의 유형별로 빠진 정보를 찾는다. 공백 하나마다:

1. 결정 사전에 해당 항목이 있으면 그 값을 쓰고 `status: "dictionary"`, `basis: "D-xx"` 로 적는다. 질문하지 않는다.
2. 없으면 질문을 만든다(체크리스트 2장 형식). **권장값과 근거를 반드시 붙인다.** 이유: 빈 질문은 기획자가 정책을 처음부터 만들어야 해서 답이 늦다.
3. 차단형/비차단형으로 나눈다(체크리스트 1장). 차단형은 기획서 1건당 최대 10개.

- 넘어가는 조건: `<out>/<기능 이름>.draft.json` 의 `gaps` 에 모든 공백이 ID·근거·권장값과 함께 있다.

### 4. 질문 전달 (기다리지 않는다)

공백 목록을 사용자에게 보여 준다. 사용자가 기획자에게 전달한다. 질문 끝에 "답이 없으면 <기한>에 권장값으로 확정"을 붙인다(기한은 사용자에게 묻고, 답이 없으면 영업일 2일 뒤).

건너뛰고 싶어지는 이유와 왜 안 되는지:

- "사소한 공백이니 권장값으로 TC 만 만들자" → 질문을 안 보내면 기획자는 가정이 있었는지도 모른다. 비차단형도 목록은 전달한다.
- "답을 받고 나서 TC 를 만들자" → 사람 합의가 병목이 된다. 답이 와도 바뀌는 건 가정이 걸린 TC 뿐이다.

- 넘어가는 조건: 공백 목록을 사용자에게 보여 줬다.

### 5. 테스트 케이스 작성

`draft.json` 의 `cases` 에 쓴다. 형식은 `<skill>/scripts/cases-to-xlsx.mjs` 상단 주석.

- TC ID: `<기능 약어>-<두 자리 번호>`. 프로젝트에 기존 체계가 있으면 따른다.
- 기대 결과 하나에 확인 하나. 이유: 한 TC 에 두 확인을 섞으면 한쪽만 틀려도 원인을 못 가른다.
- 화면 문구는 **Figma 문구 그대로** 따옴표로 쓴다. PDF 모드면 이미지로 한 번 더 확인한다(input-modes 3장).
- 권장값에 기대는 TC 는 `assumptions` 에 공백 ID 를 넣는다.
- 자동화 여부처럼 다음 단계 도구가 정하는 열은 비워 둔다. 이유: 여기서 추측하면 틀린다.
- 넘어가는 조건: 2단계의 모든 사실과 3단계의 모든 공백이 최소 한 TC 로 이어진다(아니면 이유를 `note` 에).

### 6. 엑셀 만들기

```
node <skill>/scripts/cases-to-xlsx.mjs <out>/<기능 이름>.draft.json --config .qa-cases.json
```

- 넘어가는 조건: 오류 없이 끝나고 TC 수·공백 수가 출력됐다. 오류가 나면 메시지대로 `draft.json` 을 고친다. 엑셀을 직접 고치지 않는다(다시 만들면 덮어써진다).

### 7. 보고

엑셀 경로, TC 수, 차단형/비차단형 공백 수, 사전으로 처리한 공백 수, 가정이 붙은 TC 수, MCP 호출 횟수를 알린다.

### 8. 기획자 답 반영 (답이 온 뒤 다시 호출될 때)

1. `gaps[].status` 를 `confirmed`(권장값 그대로) 또는 `changed`(`answer` 에 실제 답)로 바꾼다.
2. `changed` 공백에 걸린 TC 만 다시 쓴다. 다른 TC 는 건드리지 않는다.
3. 다른 기능에도 쓸 결정이면 결정 사전에 `D-xx` 로 추가한다(사용자 확인 후, 근거 포함).
4. 6단계로 엑셀을 다시 만든다.

## 금지

- 기획서에 없는 기대 결과를 공백 질문 없이 TC 에 넣지 않는다. 이유: 기획자도 QA 도 모르는 기준이 생긴다.
- 기획자에게 직접 메시지·댓글을 보내지 않는다. 전달은 사용자가 한다.
- 요청받지 않은 기존 엑셀·테스트 코드·설정을 고치지 않는다.
- 스냅샷(기획서 원본)을 git 에 올리지 않는다. 사내 기획 문서다.
