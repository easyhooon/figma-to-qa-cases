# 생성한 테스트 케이스와 기존 테스트 케이스 비교

`figma-to-qa-cases` 가 만든 케이스를 기존 QA 테스트 케이스와 맞대어, 생성 결과가 무엇을 더 다루고 무엇을 놓쳤는지 사실로 정리한다. 놓친 것은 원인을 둘로 나눈다: 기획서에 없는 암묵지인지, 기획서에 있는데 생성 단계가 놓쳤는지.

이 문서 기준 경로: `<skill>` = 이 SKILL.md 가 있는 폴더. 스크립트는 플러그인 루트의 `node_modules`(exceljs)를 쓴다.

## 입력

- 생성 결과: `<outputDir>/<기능 이름>.draft.json` (figma-to-qa-cases 출력). 같은 폴더의 `snapshot/frames.json` 도 쓴다.
- 기존 테스트 케이스 엑셀 경로와 시트 이름. 없으면 사용자에게 묻는다.

## 절차

각 단계의 넘어가는 조건을 만족해야 다음 단계로 간다.

### 1. 기존 케이스 읽기

```
node <skill>/scripts/xlsx-rows.mjs <엑셀> --sheet "<시트>" --out <outputDir>/<기능 이름>.existing.json
```

- 출력된 헤더가 케이스 표의 헤더가 아니면(요약 표의 글자 등) `--header-row N` 으로 다시 실행한다.
- 넘어가는 조건: 헤더에 케이스 ID 와 케이스 내용 열이 보인다.

### 2. 비교 범위 정하기

`draft.json` 의 화면 범위(`source`, 케이스의 `screen`)에 해당하는 기존 케이스만 고른다. 기능 이름 키워드로 후보를 찾고, 행 번호 구간을 사용자에게 한 번 보여 준다.

- 범위 밖 케이스(다른 화면, 다른 섹션)는 비교하지 않고 "범위 밖" 목록에 행 번호와 이유를 적는다. 이유: 범위 밖 케이스를 "생성에서 빠짐"으로 세면 누락 수가 부풀려진다.
- 넘어가는 조건: 범위 안 기존 케이스 목록(ID, 내용)과 범위 밖 목록이 있다.

### 3. 대응 짓기

범위 안 기존 케이스마다 같은 동작을 확인하는 생성 케이스를 찾는다. 하나가 여러 개에 대응될 수 있다(기존이 기능 단위, 생성이 주석 단위인 경우가 많다).

| 결과              | 기준                                                                    |
| ----------------- | ----------------------------------------------------------------------- |
| 대응              | 생성 케이스가 기존 케이스의 확인 내용을 모두 포함                       |
| 일부 대응         | 일부만 포함. 빠진 부분을 한 줄로 적는다(예: "스와이프로 날짜 변경 없음") |
| 기존에만 있음     | 대응되는 생성 케이스가 없음                                             |

생성 케이스 중 어느 기존 케이스와도 대응되지 않는 것은 "생성에만 있음"으로 모은다.

- 넘어가는 조건: 범위 안 기존 케이스 모두에 결과가 붙었다.

### 4. 빠진 부분의 원인 나누기

"일부 대응"의 빠진 부분과 "기존에만 있음" 케이스마다 `snapshot/frames.json`(필요하면 화면 이미지)에서 해당 내용을 찾는다.

| 원인                      | 기준                                  | 후속 처리                                                            |
| ------------------------- | ------------------------------------- | -------------------------------------------------------------------- |
| 기획서에 없음             | 기획서 어디에도 해당 동작이 없다      | figma-to-qa-cases 의 미정의 항목 후보. 사용자 확인 후 `draft.json` 에 미정의 항목으로 추가 |
| 기획서에 있음, 생성 누락  | 기획서에 있는데 생성 케이스가 없다    | figma-to-qa-cases 규칙 보강 후보. 어느 주석을 놓쳤는지 근거 위치를 적는다 |

- 원인을 정할 근거(기획서 위치 또는 "찾지 못함")를 반드시 적는다. 이유: 근거 없이 "기획서에 없음"으로 두면 생성 단계의 실수가 암묵지로 잘못 분류된다.
- 넘어가는 조건: 빠진 항목 모두에 원인과 근거가 있다.

### 5. 결과 저장과 보고

`<outputDir>/<기능 이름>.compare.json` 에 저장한다.

```json
{
  "existing": { "file": "...", "sheet": "...", "inScopeRows": [244, 249], "outOfScope": [{ "row": 244, "id": "236", "reason": "생활기록 홈 화면" }] },
  "matches": [{ "existingId": "241", "existing": "...", "result": "일부 대응", "generated": ["SCR-03-06-01"], "missing": "..." }],
  "generatedOnly": ["SCR-05-02-01"],
  "missing": [{ "existingId": "239", "what": "스와이프로 날짜 변경", "cause": "기획서에 없음", "basis": "SCR-03 주석 3, 4 에 스와이프 언급 없음" }]
}
```

사용자에게 알린다: 범위 안 기존 케이스 수, 생성 케이스 수, 대응/일부 대응/기존에만 있음 수, 생성에만 있음 수, 원인별 빠진 항목 목록.

- 보고에 "더 낫다", "충분하다" 같은 평가를 넣지 않는다. 이유: 수가 많다고 좋은 케이스가 아니고, 판단은 QA 담당자가 한다.

## 금지

- 기존 엑셀과 `draft.json` 을 고치지 않는다. 미정의 항목 추가는 사용자 확인 후 figma-to-qa-cases 절차로 한다.
- 앱 소스 코드로 원인을 판단하지 않는다. 비교 기준은 기획서와 두 케이스 목록뿐이다.
